这个博客从 2018 年 11 月左右就停更了。文章还在，主题还是当年的 NexT，我自己再打开仓库，都会犹豫要不要动。

今年想把它重新发布出去，也想给它一个自己的域名。我打开 Grok Bot，让它陪我看这个站。它是我在 Cursor 里用的桌面助手。我说得很笼统：这是一个停了很久的 Hexo 博客，源码在 GitHub 上，我想让它重新能打开。

它先把仓库看了一遍。文章和配置写在源码分支 `hexo` 上，GitHub Pages 读的是另一份生成好的静态页。这两边分清之后，后面的升级就不容易把源码和线上搅在一起。

一起做完的结果，我现在说得出来。Hexo 和 NexT 换到这一代还能构建的版本，Node 也换了。外观还是原来那套浅色，旧文章的地址没改。发布收成一次构建、两个出口：源码推上去之后，[alwaysloseall.github.io](https://alwaysloseall.github.io/) 和 [blog.nekodayo.com](https://blog.nekodayo.com/) 一起更新。GitHub Pages 留着，是因为以前的链接还指着那儿。

步骤我没写在这篇里。想看怎么做，可以读 [Hexo 博客升级与 GitHub Actions 双端发布教程](</2026/09/29/Hexo 博客升级与 GitHub Actions 双端发布教程/>)。事情的经过在 [从沉睡到双端发布](</2026/09/29/从沉睡到双端发布：博客升级与 GitHub Actions 记录/>)。

改代码时，我在对话里说要改什么，它在云端开 Pull Request，合进 `hexo`。合并之后，GitHub Actions 会构建，两个站一起变。我主要看改动对不对、话说得清不清楚，再决定合不合。接着改的时候，不用把仓库结构再解释一遍。

文章也是这么来的。升级做完，我想留一篇给以后的自己，再留一篇给读者。短的那篇只讲经过，教程才写步骤。对着助手往下说，很容易把内部过程全倒进去。那些对排错有用，公开读起来却像运维笔记。我让它按给人看的方式再收一收：站醒了，两个地址是同一份站点，旧链接还在。

博客要写成什么样，还是我自己定。助手跟着这个仓库走：结构怎么分、发布走哪条分支、文章该用什么语气，下一句都能接上。双端接上之后，我写完一篇、合进源码，两个地址一起更新。站又回到自己手里，这种感觉很实在。

现在两边都能打开：

- [https://alwaysloseall.github.io/](https://alwaysloseall.github.io/)
- [https://blog.nekodayo.com/](https://blog.nekodayo.com/)

如果你也有一个放了很多年的静态博客，可以先让它重新能打开。我把自己的用法记在这里：一个停了八年的站，靠来回对话和几次合并，又开始更新了。
